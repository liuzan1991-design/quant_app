# QMT 沙箱下的策略状态重建方案（v0.1 草案）

> 2026-11-06
> 前置约束：2026-11-24 起 QMT 内置策略**禁止文件读写、禁止外网/局域网**
> 相关：`移植规范.md` §0（合规硬约束）、§4（账户与持仓隔离）

---

## 1. 问题的本质

沙箱化把"状态持久化"这条路彻底堵死了。**进程重启 = 账本归零**。

这不只是"丢日志"的问题。做 T 策略的核心状态——底仓多少、T 仓多少、网格到第几档、
今日已实现多少——如果只存在内存里，那么：

- QMT 崩溃重启 → 策略失忆
- 断电重启 → 策略失忆
- 手动停止再启动（调试、改参数）→ 策略失忆

失忆的后果不是"从零开始"，而是**基于错误的假设继续下单**。例如策略以为 T 仓是 0，
实际上还有 300 股没平，于是重复买入。

**所以本方案的第一原则不是"如何持久化"，而是「一切状态必须可重建」。**

---

## 2. 设计原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | **可重建优先于可持久化** | 任何字段必须能回答："重启后我怎么从柜台或行情把它算回来？" 答不上来的字段，不允许成为决策依据 |
| P2 | **不信任内存累加器** | 禁止用 `self.cum_pnl += x` 这类跨 bar 累加的变量做关键判断；一律每 bar 重算 |
| P3 | **柜台是唯一事实来源** | 持仓、成交、资金，以 `get_trade_detail_data` 为准，不以策略内部记账为准 |
| P4 | **失忆要安全失败** | 重建不出来时，默认**停手**（只平不开 / 完全不动），绝不"猜一个值继续干" |
| P5 | **隔离靠机制，不靠人** | 理想是用委托标签区分策略仓；做不到时，必须用运营约束兜底，并把这个约束写死 |

## 3. 状态清单与重建路径

把四策略用到的状态全部列出来，逐项给出重建方式。**这是本方案的核心表**。

| 状态 | 是否可重建 | 重建方式 |
|---|---|---|
| 账户总资产 / 可用资金 | ✅ 完全可重建 | `ACCOUNT.m_dBalance` / `m_dAvailable`（每 bar 读） |
| 标的总持仓 / 可卖量 | ✅ 完全可重建 | `POSITION.m_nVolume` / `m_nCanUseVolume` |
| 昨仓量（底仓基数） | ✅ 可重建 | `POSITION.m_nYesterdayVolume` |
| 持仓成本 | ✅ 可重建（有坑） | `m_dOpenPrice`（**不能用 `m_dAvgOpenPrice`，那是 DBL_MAX 哨兵**） |
| 今日成交明细 | ✅ 可重建 | `DEAL` 表按 `m_strTradeDate == 今日` 过滤 |
| 今日委托状态 | ✅ 可重建 | `ORDER` 表按 `m_strInsertDate == 今日` 过滤 |
| 今日已实现盈亏 | ⚠️ 部分可重建 | `DEAL` 逐笔配对算，但依赖成本口径；更稳的是用"权益变化 − 未实现盈亏"反推 |
| **T 仓数量** | ⚠️ **有条件可重建** | 见 §4，**这是全方案最脆弱的一环** |
| 网格当前档位 | ✅ 可重建 | 由「基准价 + 网格宽度 + 当前价」纯函数计算，**不要存"当前第几档"** |
| MA / ATR 等指标 | ✅ 可重建 | 由 QMT 日线/分钟线重算（日线自 2023 起可用） |
| 情绪/趋势状态 | ✅ 可重建 | 由历史 K 线重算（注意要用**前一交易日**状态，见 H78 修复） |
| 累计收益曲线 | ✅ 可重建 | **`当前权益 − 初始权益`**，不做跨日累加（这也修掉了 memory 里 E1 那个"累计回撤读错文件"的坑） |
| 熔断标志（日亏/w 回撤） | ✅ 可重建 | 由当日权益变化与历史权益高点重算；历史高点可由「初始权益 + 每日权益」……**此处有缺口，见 §6** |
| 下单防重（同一决策不重复发单） | ❌ 不可重建（时间窗内） | 只能靠"下单后当场校验委托表"，或短窗口内的内存去重 + 重启后强制空窗期 |

## 4. T 仓重建：全方案的关键难点

### 4.1 为什么难

T 仓 = 「今日买入的量 − 今日卖出的量」，但**只应统计策略自己下的单**。
账户里同时有你的手工交易，所以 `POSITION` 的今日增量不纯。

### 4.2 三条候选路径（按可靠性排序）

**路径 A：委托标签（最理想）**

下单时给委托打标记，重建时按标记过滤。候选字段：

| 字段 | 现状 | 结论 |
|---|---|---|
| `m_strOrderRef` | 实测形如 `SZ_1483`，QMT 自己生成 | ⚠️ 需验证 `passorder` 是否允许自定义 |
| `m_nStrategyID` | ORDER 与 POSITION 都有，但**同笔委托与持仓取到的值不同**（`-8205645640633496769` vs `5720613610982770964`） | ⚠️ 语义未验证，暂不可用 |
| 委托备注 `remark` | 未探测 | ⚠️ 需验证 `passorder` 是否有该参数 |

⇒ **必须做一次探测**（见 §7 验证项 V1），结果决定方案走 A 还是 B。

**路径 B：数量对账 + 运营约束（保底，现在就能用）**

不做标签，改为：

1. 策略维护"理论 T 仓"，每 bar 用当日 DEAL 全量重算（不累加）
2. 每 bar 与柜台持仓比对，差额记为**外来变动**
3. 外来变动超过阈值 → 判定"有人手工动了这个标的" → **策略立即停手并告警**
4. 运营约束（写死）：**策略运行的标的，人不手工交易**

这条的代价是把"技术隔离"降级为"流程隔离"，但**零技术风险、当天就能上**。
对外来变动的检测，实际上比标签法更保守——它不假设标签一定可靠。

**路径 C：独立账户（最彻底）**

已被 Louis 否决（2026-11-04 拍板：用真实账户，不另开小账户）。
⇒ **排除**，但记录在此，将来若要重开这个决策，C 是最干净的。

### 4.3 结论

**先按路径 B 实施，同时做 V1 探测；若标签可用，再升级到 A+B 双保险。**

## 5. 每 bar 重建流程

```
handlebar(tick):
  1. 读 ACCOUNT      → equity, avail, status
  2. 读 POSITION(本标的) → vol, sellable, yvol, cost
  3. 读 DEAL(今日)   → 逐笔：时间/方向/价/量/orderRef
  4. 读 ORDER(今日)  → 未成交挂单量（必须计入，否则重复下单）
  5. 重建派生状态：
       t_lots      = 今日买入笔 − 今日卖出笔（按 §4 的归属规则）
       base_shares = yvol - 今日卖出(底仓部分)
       grid_level  = f(基准价, 网格宽, 现价)      ← 纯函数，无视历史档位
       ma/atr      = f(近期 K 线)
       day_pnl     = equity - 当日开盘权益
  6. 一致性校验：
       若 |重建出的 vol − 柜台 vol| > 0  → 记差异，按 P4 决定停手
  7. 决策 → 下单（下单金额/量按 §5 额度约束）
  8. 下单后立刻回读 ORDER，确认挂单已进入柜台（防重复发单）
```

**关键点**：第 5 步全部是"算"不是"记"。第 7 步之前不依赖任何跨 bar 变量。

## 6. 已知缺口（不可重建的部分，必须显式处理）

| 缺口 | 影响 | 处置 |
|---|---|---|
| **历史权益高点**（用于回撤熔断） | 重启后无法知道历史最高权益 | 用 `ACCOUNT` 无此字段 ⇒ 改为**只做日内熔断**，跨日回撤熔断降级为"由外部脚本读日志重算并展示"，策略内不决策 |
| **当日开盘权益** | 重启后拿不到 | 用 `m_dPreBalance`（昨结算权益）替代，实测有该字段 |
| **跨 bar 的下单节流**（如同一天同一档只发一次） | 重启后可能重复发单 | 靠回读 ORDER 表判断"该档是否已有挂单"，不靠内存标记 |
| **策略自定义参数** | 不能读配置文件 | 全部硬编码为源码常量；改参数 = 改源码 + 重启 |

## 7. 必须先验证的项（V1 优先）

| 编号 | 验证内容 | 为什么卡 |
|---|---|---|
| **V1** | `passorder` 是否支持自定义 `orderRef` / `remark`；`m_nStrategyID` 是否稳定可作标签 | 决定 T 仓归属走路径 A 还是 B |
| V2 | `POSITION.m_nYesterdayVolume` 在 T+1 下是否严格等于"昨日收盘持仓" | 决定底仓基数怎么算 |
| V3 | 重启一致性：bar N 重启 vs 不重启，重建出的状态是否完全一致 | 方案有效性的直接检验 |
| V4 | 手工交易干扰：人为买/卖该标的，策略是否在下一 bar 正确识别为外来变动 | 路径 B 的核心能力 |
| V5 | `DEAL` 表能否取到**当日全部**成交（笔数上限？） | 成交多时是否会截断 |

## 8. 实施顺序

1. **V1/V2 探测**（一个小 probe，1 次盘内运行即可）
2. 按 §5 写 `state_rebuild.py`（纯函数：输入四张表 → 输出状态 dict）
3. 单元测试：用 §7 的 V3/V4 场景做离线验证（本地 mock 柜台数据，不碰 QMT）
4. 接入只读运行器：每 bar 打印重建结果，与柜台直接读数对比
5. 稳定后，才允许它参与下单决策

## 9. 与 H59 的关系

H59 的根因是「`state` 每日 reset 但 `acc.t_lots` 跨日累积」——本质是**两套账本不同步**。

本方案直接消灭这个结构性问题：**不再有两套账本**。只有一套"每 bar 从柜台重建"的派生状态，
不存在"跨日累积"这个动作，也就没有同步问题。

⚠️ 但这不等于 H59 自动修好。H59 的**业务逻辑**（止损时卖多少、兜底能否卖到底仓）
仍需按原设计逐条验证。本方案解决的是"账本为什么会不一致"，不是"止损该卖多少"。
